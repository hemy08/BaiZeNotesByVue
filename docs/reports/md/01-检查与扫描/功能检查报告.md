### FUN-01 预览渲染无 HTML 消毒，恶意 Markdown 可触发任意 IPC/启动本地程序 <span>P0</span>
 → ✅ 已修复

- **位置**：`src/renderer/src/components/Markdown/MarkdownPreviewComponent.vue:32-39`、`:5`；`src/renderer/src/components/Markdown/hemy-editor-render.ts:152-154`；`src/preload/index.ts:48-51`；`src/main/utils/utils.ts:105-107`
- **描述**：MarkdownIt 以 `html: true` 初始化且未挂任何消毒插件；`PostMarkdownRender` 对 HTML 原样返回；模板直接 `v-html="renderedMarkdownContent"`。渲染进程 webPreferences 虽为 `nodeIntegration:false, contextIsolation:true, sandbox:true`（main/index.ts:30-37，做得好），但 preload 通过 `contextBridge.exposeInMainWorld('electron', electronAPI)` 把 `@electron-toolkit/preload` 的完整 `ipcRenderer`（send/invoke/on）暴露给页面上下文。
- **证据**：
  - `MarkdownPreviewComponent.vue:32` `const md = MarkdownIt({ html: true, ... })`；`:5` `<div ... v-html="renderedMarkdownContent">`
  - `hemy-editor-render.ts:152` `export function PostMarkdownRender(text: string): string { return text }`
  - `utils.ts:105-107` `ipcMain.on('navi-tab-open-exe', async (_, exePath: string) => { await shell.openPath(exePath) })`
- **影响**：打开恶意 .md 文件即可在预览中执行任意脚本，可调用 `window.electron.ipcRenderer.send('navi-tab-open-exe', ...)` 启动任意本地程序（shell.openPath），或 `open-external-link` 打开任意 URL、`config:write` 篡改配置——XSS 升级为本地任意程序启动。
- **修复建议**：渲染管线末端接入 DOMPurify（生产依赖中已存在该库）；preload 只暴露白名单式窄 API（不暴露通用 ipcRenderer）；主进程对 `navi-tab-open-exe`/`open-external-link`/`config:*` 等渠道做调用来源与参数校验。
- **工作量**：2-3 人日（含回归）

### FUN-02 编码体系整体失效：乱码回写覆盖 + 编码菜单无监听 <span>P1</span>
 → ✅ 已修复

- **位置**：`src/main/utils/file-utils/file-operations.ts:381`、`:344`；`src/main/utils/file-utils/auto-save.ts:27`；`src/main/ipc/menu_file.ts:6-12`
- **描述**：打开文件一律 `fs.readFile(path,'utf8')`，无任何编码探测（仅 CSV 导入做了 jschardet，import.ts:143-146）；GBK/GB2312 文件打开即乱码（替换字符）。更严重的是：自动保存不查脏标记，30 秒内会把乱码内容以 UTF-8 回写，**破坏原文件**。而菜单提供的"重新用…编码打开 / 转为…编码"（menu_config.ts:108-150）由主进程 `send('open-with-encoding'/'convert-to-encoding')`（menu_file.ts:6-12），全渲染端没有任何 `ipcRenderer.on` 监听这两个频道（全库 grep 仅命中 menu_file.ts 与 ipc-channels.ts），即编码菜单全部无效，用户连"重新用 GBK 打开"的补救手段都没有。
- **证据**：
  - `file-operations.ts:381` `let data = await fs.readFile(fileProperties.path, 'utf8')`
  - `auto-save.ts:27` `if (appState.currentActiveFile && appState.currentActiveFile.content) {` → 每 30s `SaveActiveFile()` 以 utf-8 写回（file-operations.ts:58）
  - `menu_file.ts:7` `mainWindow.webContents.send('open-with-encoding', encoding)`，渲染端无监听
- **影响**：非 UTF-8 文件打开乱码，且静默损坏原文件（数据丢失）；编码切换功能整体是空壳。
- **修复建议**：打开时用 jschardet/iconv 探测编码并保留"当前编码"状态；自动保存前若编码与磁盘不一致则要求用户确认；在 MarkdownEditComponent/独立组件中实现 open-with-encoding / convert-to-encoding 监听（主进程重读文件按指定编码解码并更新 appState 与编辑器）。
- **工作量**：2 人日

### FUN-03 关闭窗口不保存、无未保存确认 <span>P1</span>
 → ✅ 已修复

- **位置**：`src/main/ipc/handlers.ts:31-33`；`src/main/index.ts:141-146`；`src/renderer/src/components/StatusBar.vue:96`
- **描述**：标题栏关闭按钮发送 `window-close` → `mainWindow.close()`，主窗口无任何 `close`/`before-quit` 拦截保存逻辑；渲染端也未监听 `beforeunload`。未保存标记（isUnsaved）只用于状态栏红点展示，没有任何流程消费它。自动保存间隔默认 60 秒（system-setting.ts:17），用户在最后一次修改后 60 秒内点关闭（或退出、或"重启应用"菜单 menu_file.ts:27-30），修改静默丢失。
- **证据**：
  - `handlers.ts:31-33` `ipcMain.on('window-close', () => { if (mainWindow) mainWindow.close() })`
  - `StatusBar.vue:96` `isUnsaved.value = true`（仅显示用途）
  - `main/index.ts:141-146` `window-all-closed → app.quit()`，无保存逻辑
- **影响**：高频数据丢失风险；与"自动保存"形成 60 秒数据丢失窗口。
- **修复建议**：mainWindow.on('close') 中先同步待保存内容并落盘（或弹未保存确认）；退出/重启前同样处理。
- **工作量**：1 人日

### FUN-04 自动保存开关反向失效 + 设置双轨存储 <span>P1</span>
 → ✅ 已修复

- **位置**：`src/main/ipc/handlers.ts:148-150`；`src/renderer/src/components/dialogs/complex/SystemSettingDialog.vue:235-256`；`src/main/index.ts:88-90`；`src/main/config/system-setting.ts:10`；`src/main/config/config-manager.ts:39`
- **描述**：系统设置对话框修改自动保存后发送 `system-setting-auto-save-changed`，主进程处理器**无条件** `StopAutoSaveFileTime()` 且忽略 payload、从不按新参数重启；因此"打开自动保存"操作实际效果是停掉自动保存，修改间隔也不生效（间隔只在启动时读一次：index.ts:88-90）。同时渲染端把设置写入 `system.json`（config-manager，L256 `window.api.config.write('system', ...)`），而主进程读的是 electron-store 的 `systemSetting.json`（system-setting.ts:10）——两套存储互不同步。
- **证据**：
  - `handlers.ts:148-150` `ipcMain.handle('system-setting-auto-save-changed', () => { StopAutoSaveFileTime() })`
  - `SystemSettingDialog.vue:237` send(...) / `:256` `window.api.config.write('system', ...)`
  - `main/index.ts:89` `const autoSaveInterval = (systemSetting.autoSaveInterval || 30) * 1000`
- **影响**：用户关掉再打开自动保存后自动保存实际处于关闭状态；间隔设置无效；"系统设置"与主进程实际行为脱节。
- **修复建议**：处理器按 payload 的 autoSaveEnabled/autoSaveInterval 调 StartAutoSaveFileTime(newInterval)；统一系统设置为单一存储（建议以 electron-store 为准，删除 system.json 写入路径）。
- **工作量**：1 人日

### FUN-05 自动保存不检查脏标记、空内容跳过、失败静默 <span>P1</span>
 → ✅ 已修复

- **位置**：`src/main/utils/file-utils/auto-save.ts:25-36`
- **描述**：注释宣称"只有当文件有修改时才保存"，但条件 `if (appState.currentActiveFile && appState.currentActiveFile.content)` 检查的是"内容非空"，而非脏标记。后果：①每 30/60 秒无条件重写文件（无修改也写，mtime 抖动、干扰外部同步工具与"文件被外部修改"判断）；②用户清空文件内容后（content===''）自动保存永不触发，空文档不会落盘；③`SaveActiveFile` 内部已 catch 并弹窗（file-operations.ts:69-72），此处再 catch 仅 console.error，实际失败时用户未必看到（SaveActiveFile 弹窗后吞掉错误）。
