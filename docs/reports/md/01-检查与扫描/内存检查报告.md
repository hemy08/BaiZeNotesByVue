## 3. 逐项发现

### MEM-01 字体选择对话框监听器无效移除与残留（P1）
 → ✅ 已修复

- **位置**：`src/main/dialogs/ShowFontSelectDialog.ts:66-70`、`:110-114`
- **证据**：

```typescript
// L66-70：移除时传入的是"新的空匿名函数"，与注册时的引用不同 → 移除无效
ipcMain.removeListener('dialog-user-font-select-btn-insert', processCustomFontDialogApply)
ipcMain.removeListener('dialog-user-font-select-btn-cancel', () => {})   // ❌ 无效移除
win.close()

// L110-114：cancel 监听器本身就是匿名函数，永远无法按引用移除
ipcMain.on('dialog-user-font-select-btn-insert', processCustomFontDialogApply)
ipcMain.on('dialog-user-font-select-btn-cancel', () => { exitFontSelectDialog() })
```

- **影响**：每次打开对话框注册 2 个监听器；正常"取消/应用"路径可移除 insert（引用正确）但 **cancel 监听器永远残留**；用户点击系统标题栏关闭按钮（而非对话框内按钮）时 `exitFontSelectDialog` 不执行，**insert 也残留**。残留监听器闭包捕获 `mainWindow`，长期运行累积。基线报告（2026-05-02 §8.1 问题 1）将此类问题列为"必须修复"，此文件仍未修复。
- **修复建议**：将 cancel 改为命名函数 `processCancel`；把清理逻辑挂到窗口 `closed` 事件（`windowManager.createWindow` 返回的窗口已自动注册 closed → 清理 Map，但直连 ipcMain 监听器需自行在 closed 中 removeListener）；或改用 `ipcListenerManager.register`。
- **工作量**：0.5 小时

### MEM-04 导入选项对话框 ipcMain.once 残留与多重触发（P1）
 → ✅ 已修复

- **位置**：`src/main/dialogs/ShowImportOptionDialog.ts:62`；HTML 内 `:283`、`:320` 的 `window.close()`
- **证据**：

```typescript
// L62：once 仅在事件触发时自动移除
ipcMain.once('import-option-confirm', async (_event: any, option: ImportOption) => {
    ...
    windowManager.getWindowByType('import-option-dialog')?.close()
    onConfirm(option, filePath)
})
// 对话框 HTML 提供两条不触发该事件的关闭路径：
// L283  <button class="close-btn" onclick="window.close()">x</button>
// L320  <button class="btn btn-cancel" onclick="window.close()">取消</button>
```

- **影响**：用户通过"×"或"取消"直接关窗时 `import-option-confirm` 从未触发 → once 监听器残留（闭包捕获 `mainWindow` 与 `onConfirm` 回调，后者来自调用方 import 流程，可能持有大文件内容）。用户多次"打开→取消"后监听器逐个累积；**下一次真正确认时，所有残留 once 一次性全部触发**：旧回调会关闭当前新对话框并重复执行 `onConfirm`，导致功能错乱（导入选项被重复处理）。这是本轮检查中功能+内存双重风险最高的一项。
- **修复建议**：改为 `ipcMain.on` + 窗口 `closed` 事件 `removeListener`（或改走渲染进程现有 Vue 对话框流程——注意主进程 `ShowImportOptionDialog` 目前已无调用方，渲染进程改用 `ImportOptionDialog.vue`，此文件可考虑整体下线）。
- **工作量**：0.5 小时

### MEM-05 文件内容缓存"只写不读"（P2）
 → ✅ 已修复

- **位置**：`src/main/utils/baize-store.ts:26-27,84-96`；写入方 `src/main/utils/file-utils/file-operations.ts:61,345,386`
- **证据**：`setFileContent` 在 3 处被调用（保存、自动保存、打开文件），全项目 grep 确认 `getFileContent` / `hasFileContent` / `deleteFileContent` **没有任何调用方**。缓存上限 `MAX_CACHE_SIZE = 50` 只按文件数计算（FIFO 近似，非 LRU）。
- **影响**：每保存/打开一个文件就把完整内容复制进 `fileCache` Map，但从不回读——50 个大文件（单个可达 5MB+，`LARGE_FILE_THRESHOLD` 之上仍被缓存）可能纯驻留数十至数百 MB 内存且无收益。同时因按数量而非字节数淘汰，大文件场景驻留量不可控。
- **修复建议**：二选一——(a) 删除 `fileCache` 及其 3 处写入；(b) 真正接入读取路径（如文件切换时命中缓存跳过磁盘读），并增加字节预算淘汰策略。
- **工作量**：1 小时

### MEM-07 PDF 导出隐藏窗口异常路径泄漏（P2）
 → ✅ 已修复

- **位置**：`src/main/utils/file-utils/export.ts:263-305`
- **证据**：`ToPdf` 中 `new BrowserWindow({ show: false })`（L263）不经过 `windowManager`；`win.close()`（L305）仅在成功路径执行。若 `loadURL` / `printToPDF` 抛异常，函数提前返回，隐藏窗口及 webContents 残留。

### MEM-08 ipcListenerManager.cleanupComponent 通道名拆分缺陷（P2，待验证）
 → ✅ 已修复

- **位置**：`src/main/ipc/ipc-listener-manager.ts:36,84`
- **证据**：`listenerId = \`${channel}:${Date.now()}:${random}\``（L36），清理时 `const [channel] = listenerId.split(':')`（L84）。若 channel 本身含冒号（如 `'baize-notes:xxx'`），拆分得到的 channel 名被截断，`this.listeners.get(channel)` 查不到 → `ipcMain.removeListener` 不会执行，清理静默失败。
- **影响**：当前通过 manager 注册的通道（`file-manager-context-menu-*`、`dialog-editor-setting-*`）均不含冒号，**缺陷暂未触发（待验证）**；一旦后续按项目惯例（大量通道名带 `baize-notes:` 前缀）接入新通道，即产生静默泄漏。
- **修复建议**：`ListenerInfo` 中直接存 channel 字段；`componentListeners` 映射 listenerId → `{ channel, listener }`，避免字符串解析。
- **工作量**：1 小时（含单测）
