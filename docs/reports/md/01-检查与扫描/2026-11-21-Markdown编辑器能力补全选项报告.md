# Markdown 编辑器能力补全选项报告（2026-11-21）

> **性质**：产品能力选项与决策清单（非缺陷报告）。用于维护者勾选后续版本要支持的功能。
> **项目基线**：v1.5.0（2026-11-21 已发布，tag `release-1.5.0`），HEAD `0dd89b5`，Node 26.13.1。
> **结论先行**：当前基础编辑/预览/渲染/安全/主题/导入导出已较完整；主要能力缺口集中在 **多文档工作流、全局检索、文档历史、Markdown 规范与元数据、知识库关联、扩展性、跨平台/协作**。
> **使用方式**：在 §4 的勾选表中选择「优先做 / 后续做 / 不做」，或直接回复套餐编号（如 `套餐 A + B1`）。

## 2. 能力候选矩阵

> 估算口径：**S** ≤2 人日、**M** 3~5 人日、**L** 8~15 人日、**XL** >15 人日（单人）；实际随交互细节/测试量浮动。推荐度按「对 Markdown 编辑器核心体验的收益/成本」排序。

### 推荐实施顺序

1. **先做低风险高收益**：A4（lint/format）→ A5（front matter）→ A7（智能输入）→ C3（打印）；
2. **再做工作流核心**：A1（多标签/会话）→ A2（全局搜索）→ A3（历史/diff）；
3. **按定位二选一**：知识库路线接 B1/B2/B4/B5；发布路线接 C1/C2/C4；
4. **平台/生态最后**：D2 → D3 → D1；D4/D5/D6 需单独立项评估。

## 5. 关键风险与依赖提示

- **A1 多标签**不是纯 UI：需要重构「当前文档」状态、保存/关闭协议、启动恢复与 E2E，建议单独一个版本做；
- **A2/B2 索引**会影响主进程性能与目录监听链路，必须定义忽略规则（`node_modules/.git` 等）与增量更新；
- **A3 历史**需要存储上限与清理策略，不能无界增长；与自动备份是两个能力，不要混用；
- **B1/B4** 会改变文件语义（链接/重命名），要先定链接语法、歧义规则与相对路径策略；
- **D3 mac/Linux** 的前置是代码签名/entitlements/平台测试设备，成本常被低估；
- **D5/D6** 涉及后端、隐私与成本，建议先明确产品定位再立项；
- 当前 **单文件架构、Windows-only、未签名** 是上述能力的共同约束，规划时需一起考虑。

## 6. 建议验收标准（选定后补）

- 每一批功能必须有：单元测试 + 关键 E2E + 不降低现有覆盖率阈值；
- 不破坏现有门禁：typecheck / ESLint 0 warning / Prettier / vitest / E2E / audit / budget / fuses；
- 性能敏感功能（搜索、索引、多文档、预览）需给出量化基线（启动、内存、搜索耗时）；
- 涉及文件语义的能力（链接、重命名、历史）必须有回滚方案与失败提示。
