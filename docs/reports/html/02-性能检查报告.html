3. 逐项发现

PF-01 每次击键将整篇文档经 IPC 发送主进程 P1 ✅ 已修复

位置：src/renderer/src/components/Markdown/MarkdownMonacoEditor.vue:198-204、MarkdownEditComponent.vue:113-116、src/main/utils/utils.ts:142-148 ｜ 影响：大文档编辑卡顿，输入延迟随文档大小线性增长 ｜ 工作量：0.5~1 天

Monaco 的 onDidChangeModelContent 在每次内容变化（每次击键、每次粘贴）时执行 getValue() 取出整篇文档并 emit('update:code')；父组件 handleMarkdownCodeUpdate 随即把整篇内容经 ipcRenderer.send('update-select-file-content', newValue) 发给主进程，主进程再写入 appState.currentActiveFile.content。全链路无任何防抖/节流/增量。1MB 文档意味着每击键一次完成 1MB 字符串的序列化 + IPC 传输 + 反序列化。

// MarkdownMonacoEditor.vue
editorInstance.onDidChangeModelContent(() => {          // L198
    const context = editorInstance.getValue()           // L200 整篇取值
    emit('update:code', context)                        // L201
})
// MarkdownEditComponent.vue
function handleMarkdownCodeUpdate(newValue: string) {
    window.electron.ipcRenderer.send('update-select-file-content', newValue) // L114
    markdownEditorContent.value = newValue
}
// utils.ts
ipcMain.on('update-select-file-content', async (_, content: string) => {  // L142
    appState.currentActiveFile.content = content
})

修复建议：编辑同步改为「脏标记 + 空闲回调」或 300~500ms 防抖；主进程仅保存元数据/摘要，正文在 Ctrl+S、自动保存、切文件时一次性传输；或使用 Monaco onDidChangeModelContent 的 change 事件做增量 diff。

PF-02 预览渲染四跳 IPC + markdown-it 双次全量解析 + 主进程同步 KaTeX P1 ✅ 已修复

位置：MarkdownPreviewComponent.vue:84-101、utils.ts:31-37、HemyRender.ts:118-148、KatexRender.ts:65-76、hemy-editor-render.ts:117-150 ｜ 影响：输入 150ms 防抖后整篇文档在 4 次 IPC 间往返；含公式文档在主进程同步跑 KaTeX，冻结主进程事件循环 ｜ 工作量：1~2 天

预览链路：渲染进程把整篇文本发主进程（pre-render）→ 主进程 HemyRenderPre 同步执行 KaTeX 渲染全部公式（katex.renderToString 无缓存）及正则替换后发回 → 渲染进程执行 mermaid 渲染 + md.render()（markdown-it 全量解析+highlight.js）→ 又调用 ParserMarkdownChapters 用 md.parse 再解析一遍全文提取大纲（内部对每个 token 用 indexOf 定位，O(标题数×token数)）→ 再把渲染好的 HTML 发主进程做后处理 → 发回后 v-html 整体替换。整篇文档在 IPC 边界被序列化 4 次，全文被 markdown-it 解析 2 次，且 KaTeX 同步阻塞主进程。

// MarkdownPreviewComponent.vue

function updateMarkdownPostRender(text: string) {
    UpdateMarkdownChapters()                                // L90 第二次全文解析

}
// HemyRender.ts
result = katexRenderMathInText(result)   // L121 主进程同步 KaTeX
// KatexRender.ts

// hemy-editor-render.ts
const mdTokens = md.parse(text, {})      // L120 与 md.render 重复解析
let nextToken = mdTokens[mdTokens.indexOf(token) + 1]  // L134/143 O(n²) 定位

修复建议：渲染管线整体收敛到渲染进程（KaTeX 无需主进程能力）；md.parse 结果复用（render 与 TOC 提取共用一次 tokenize）；公式/图表按内容 hash 缓存；大纲提取改线性遍历。

PF-03 Monaco 无 worker 配置（主线程回退）+ 全量打包 + 15MB 死 worker 产物 P1 ✅ 已修复

位置：electron.vite.config.ts:4、out/renderer/assets/index-WYqTEcbJ.js:33789、out/renderer/index.html:5-22 ｜ 影响：语法高亮/分词在主线程执行，长文档输入易卡顿；首屏需解析 10.4MB 主 chunk；15MB 从未被加载的 worker 文件浪费安装体积 ｜ 工作量：0.5~1 天

vite-plugin-monaco-editor 的引入与使用均被注释（electron.vite.config.ts L3-4），渲染进程用裸包名 import * as monaco from 'monaco-editor'（9 处），Vite 因此把 monaco 全部语言与功能打进主 chunk（实测 out/renderer/assets/index-*.js 10.4MB）。全源码无任何 MonacoEnvironment.getWorker 配置，产物中存在官方回退分支：console.warn("Could not create web worker(s). Falling back to loading web worker code in main thread, which might cause UI freezes...")（index-*.js:33789）。同时 ts.worker（11.3MB，含整套 TypeScript 语言服务）、css.worker（1.7MB）、html.worker（1.1MB）、json.worker（0.85MB）被打包为独立 chunk，但 index.html 并未引用它们——纯死重（本项目只使用 markdown 语言）。运行时回退警告是否实际打印，待验证（需启动打包产物观察控制台）。

修复建议：启用 vite-plugin-monaco-editor（或手写 MonacoEnvironment.getWorker 用 new Worker(new URL('monaco-editor/esm/vs/editor/editor.worker.js', import.meta.url))）并只保留 markdown 语言贡献；TS/HTML/JSON worker 产物随插件启用后不再产生。

PF-05 目录树全量重扫 + 整树 JSON 串行化过 IPC，无 fs.watch 增量机制 P1 ✅ 已修复

位置：file-operations.ts:176-254,295-318,433-439,509-515,555-561,594-600、index.ts:17,126-127、ResourceManager.vue:107-113 ｜ 影响：大目录下每次增删改/重命名/导入都触发 500ms 后全量递归扫描 + JSON.stringify 整树 + 整树 IPC；深度嵌套时 acc.find 使单层归并退化到 O(n²) ｜ 工作量：1~2 天

TraverseDirectory 递归读取全目录并对每层做 reduce 归并（acc.find((dir) => dir.path === item.path)，L236-248，对 n 个条目 O(n²)）。所有目录操作（创建/重命名/删除/导入/打开目录/手动刷新）统一 setTimeout(500ms) 后调用 ReloadDirFromDisk() 全量重扫，并 webContents.send('baize:notes:resource:manager:file-system-data', JSON.stringify(fileTree))（L318）把整棵树序列化发给渲染进程。项目声明了 watchers: fs.FSWatcher[]（index.ts L17）但从未 push 任何 watcher（清理逻辑 L126-127 只能关掉空数组），即完全没有 fs.watch/增量刷新，外部程序改动文件也不会自动出现在目录树（功能缺口，待验证：外部改动需手动右键"从磁盘重新加载"）。

// file-operations.ts
const existingDir = acc.find((dir) => dir.path === item.path) // L238 O(n²)
appState.mainWindow!.webContents.send('baize:notes:resource:manager:file-system-data',
    JSON.stringify(fileTree))                                    // L318
// CreateFileFolder / CreateFile / CreateDirectory / Rename / Delete 中：
setTimeout(async () => { await ReloadDirFromDisk() }, reloadFromDiskTime)
// L295-302 / L433-439 / L509-515 / L555-561 / L594-600

修复建议：目录操作后就地增量更新树（返回变化节点 patch）；引入 fs.watch(dir, { recursive: true })（Node 20+ 支持）带 200~500ms 防抖合并；IPC 只发送变更部分；文件树配合虚拟滚动。
