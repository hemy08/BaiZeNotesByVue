  • 方法：以架构文档声称的设计为对照，逐一核对 10 个检查重点：① 进程边界与安全；② IPC 架构；③ 状态管理；④ 模块耦合与边界泄漏；⑤ 循环依赖；⑥ 插件架构；⑦ EventBus 与 IPC 职责；⑧ 构建与部署；⑨ 测试架构；⑩ 常量与魔法值。全部发现均给出 文件:行号 证据；无法静态确认的运行时行为标注"待验证"。

2.2 现状小结

项目在进程安全基线（contextIsolation+sandbox+禁用 nodeIntegration）上做得正确，EventBus/AppState/WindowManager 等基础设施有单例与清理意识。但架构处于双轨演进状态：主进程的"JSDOM 生成 HTML 对话框 + 反射式菜单处理器树"旧架构与渲染层的"Vue 对话框 + useConfigStore + EventBus"新架构并存且互相抢占路由；配置持久化存在两套系统、三个目录；IPC 通道常量文件零引用；主进程与渲染进程存在双向运行时 import。整体呈"新旧架构未完成迁移"的中间态。

4. 逐项发现

ARC-01 远程内容窗口继承特权 preload，构成远程→主进程任意能力调用链（P0）

→ ✅ 已修复

  • 位置：src/main/dialogs/OpenOnlineWebPages.ts:6-13、src/preload/dialog.ts:4-13、src/main/utils/utils.ts:105-107、src/main/dialogs/dialog-defaults.ts:4-11
  • 描述：OpenOnlineWebPageWithDialog 用 createDialogOptions 创建窗口——该工厂强制注入 DIALOG_WEB_PREFERENCES，其 preload 为 dialog.js；随后对任意远程 URL 执行 loadURL(url)。dialog.js 通过 contextBridge 暴露了 ipcRenderer.send(channel, ...args)（不校验通道名）与 shell.openExternal。而主进程存在多个"能力型"通道：navi-tab-open-exe → shell.openPath(exePath)（任意路径执行本地程序）、open-external-link → shell.openExternal(url)、baize:notes:open-specific-folder 等，均无来源与参数校验。任何被加载的远程页面都可直接调用这些通道。
  • 证据：
    • OpenOnlineWebPages.ts:7-12：windowManager.createWindow('online-web-page', createDialogOptions({...})) 后 loadURL(url)；
    • dialog-defaults.ts:4-11：DIALOG_WEB_PREFERENCES 含 preload: DIALOG_PRELOAD（dialog.js），createDialogOptions 对所有窗口合并该 preload；
    • src/preload/dialog.ts:4-13：send: (channel, ...args) => ipcRenderer.send(channel, ...args) 无通道白名单；
    • src/main/utils/utils.ts:105-107：ipcMain.on('navi-tab-open-exe', (_, exePath) => shell.openPath(exePath))；
    • src/main/config/system-setting.ts:14：pluginOpen: 'browser'（默认外部浏览器，但可在系统设置中切换为 local-dialog，OpenOnlineWebPages.ts:20-26 按此分支）。
  • 影响：若被加载站点被劫持（或 URL 被注入），远程内容可经由 IPC 让主进程执行本地程序/打开任意链接，等同于以应用权限执行任意命令；同类窗口 OpenMermaidRenderFrame.ts:68-73 从 jsdelivr CDN 加载远程脚本到带同一 preload 的隐藏窗口，扩大攻击面。
  • 修复建议：① 远程内容窗口一律不挂 preload（用独立无特权窗口或纯 BrowserView）；② 主进程对 navi-tab-open-exe/open-external-link 等通道做路径/协议白名单与来源校验（sender 校验）；③ mermaid/katex 等远程脚本改为本地资源打包。
  • 工作量：2-3 人日。
